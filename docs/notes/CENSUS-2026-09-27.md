# BIOS census, first run, 2026-09-27

What the corpus asks of the BIOS, measured on the real one. The numbers here are
a snapshot; the ledgers in `ledger/census-*.tsv` are the record, and
`cargo run --release -p coleco-runner --bin census -- --bios bios/coleco.rom --out ledger dumps/corpus`
regenerates them in about 4 seconds.

**Scope.** One dump per title (good if there is one, never a bad one): 212
titles, 164 commercial and 48 public domain. Official releases number
146; "commercial" here means everything not public domain, so it also holds
prototypes, test cartridges and later commercial homebrew. Each title runs 25 s
under the same input script as `smoke`.

**What it cannot see.** Only what those 25 s exercised. A routine first called
on level 3 or at game over is absent. "Covered" below means covered for what
the script reached.

## 1. Entry points: the HLE's work list

87 distinct BIOS addresses are entered from cartridge code. They fall into
three groups:

- **The jump table at `$1F61`-`$1FFD`**, the documented way in. The top 15
  entries are all here, each used by 60 to 176 titles.
- **The RST vectors `$0008`-`$0038`**, used by up to 62 titles. What these do
  in the real BIOS (jump on to cartridge vectors, or something else) is to be
  read off the BIOS before implementing them.
- **Direct calls into the BIOS body**, bypassing the table: `$080B`, `$18D4`,
  `$1D01` and others, each by 7 titles or fewer. The HLE must honour these
  exact addresses too, which rules out any design that only knows the table.

Coverage of the 164 commercial titles if the HLE implements the N most-used
entries, counting a title covered when every entry it used is:

| N entries | titles fully covered |
|---:|---:|
| 0 | 15 |
| 19 | 41 |
| 27 | 75 |
| 33 | 97, the first majority |
| 40 | 132 |
| 87 | 164 |

The 15 that call nothing after boot include Pac-Man, Dig Dug, Galaxian,
Defender, Centipede, Joust and Miner 2049er: largely the Atarisoft ports.
They need the hand-over (section 3) and, for some, the font (section 2), but no
routine at all.

Share of running time spent in BIOS code once the cartridge has started,
commercial titles: median 19%, quartiles 8% and 46%, maximum 92%.

## 2. BIOS bytes read as data

71 of 164 commercial titles read BIOS bytes as data, not only call it. Almost
all of it is one thing: **the character set.** Games fetch pointers from
`$006A`-`$006D` and copy font patterns from roughly `$14C3`-`$18A2` into VRAM.
`$0069` is also read, by a few; commonly described as the 50/60 Hz flag, not
yet confirmed here.

So the HLE has to present bytes, not only behaviour: pointers at `$006A`-`$006D`
and a font where they point. The glyphs must be our own drawing, since the
BIOS's are not ours to ship. A game that draws its title in the BIOS font will
show our font, which is acceptable; a game that assumes a glyph's exact bit
pattern (collision against text, say) would notice, and the corpus will say if
any does.

Outliers, to read individually: Final Test Cartridge reads all 8 KB (a test
cart, likely a checksum); Q-bert II reads 3896 scattered bytes; Boulder Dash
reads `$0001`-`$00FA` and `$0439`-`$0531`; Monkey Academy reads byte pairs
that look like jump-instruction operands.

## 3. The RAM contract

Split in two, because they ask different things:

- **At hand-over** (bytes the game reads as the boot left them): 75 bytes, all
  but 16 of them zero. The non-zero ones sit at `$73AD`-`$73FE`, one to three
  titles each: the stack as the BIOS leaves it, and a few variables. Clearing
  RAM, setting those, and leaving SP where the BIOS does covers it.
- **During play** (bytes a BIOS routine wrote that the game then read, stack
  pops excluded): 865 bytes, of which only 29 are read by 10 titles or more.
  Five by 40 or more: `$73C4`, `$73EE`-`$73F1`. Then `$73C8`-`$73C9`,
  `$73F6`-`$73F7` and a cluster at `$7000`-`$7036`. The long tail (836 bytes
  in 1 to 9 titles each) is routines writing into buffers the game supplied,
  which is the routines' output, not state at fixed places.

The first run reported 975 bytes. That was two mistakes, both fixed in the
probe and tested: the boot-time clear counted as a contract, and stack pops of
return addresses the BIOS pushed counted as reads.

## 3b. Returns into the BIOS (added the same day)

The first census counted only calls. Building the HLE turned up Heist
returning to `$0100` through a stack word, which the census had deliberately
not counted, because most returns into the BIOS are the BIOS resuming. The
probe now keeps returns apart, and leaves out the two ordinary kinds: a return
to just after a CALL or RST in the real BIOS (a call-back finishing), and a
return to wherever an NMI interrupted BIOS code (the cartridge's handler
resuming it, by RETN or by a plain RET; the probe records each interrupted
address to recognise these). A first attempt without the second rule reported
487 addresses, then 160; with it, **5**:

| address | titles |
|---|---|
| `$03C6`, `$0461` | 7 each: Artillery Duel, Carnival, Destructor and others |
| `$0100` | Heist |
| `$0244` | Illusions |
| `$1AE1` | Mr. Do's Castle |

These are part of the HLE's surface exactly like entry points: a game that
returns there runs whatever the BIOS has there. `ledger/census-returns.tsv`.

## 4. What this settles about where the HLE intercepts

The open question was: trap at entry addresses, or synthesise an 8 KB image.
The census says **both**:

- An image must exist, because 71 titles read bytes from it and some enter it
  at addresses outside the table. It holds our own font, the header bytes at
  `$0069`-`$006D`, and something at every entry address.
- The behaviour lives in host code, reached by trapping the PC at the entry
  addresses. That keeps the routines readable and testable against the real
  BIOS one at a time.

For save states this means: the image is content (regenerated, never saved),
and any HLE state that is not in guest RAM goes into the state block, with the
version bumped. The aim is to keep that host-side state at zero by putting what
the real BIOS keeps in RAM where the real BIOS keeps it, which section 3 has
now located.

## Suggested order

1. The hand-over: RAM, stack, VDP registers as the BIOS leaves them, and the
   image with our font. Measured against the 15 titles that call nothing.
2. Entry points in census order, each diffed against the real BIOS on the
   titles that use it, until the curve passes 97 titles (33 entries), then on.
3. The outliers by name.

The boot delay is a separate decision; nothing above depends on it.
